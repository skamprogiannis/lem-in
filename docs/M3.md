# M3 — Simulation

## 1. What M3 was supposed to achieve

Per `PRD.md` §8.3 and §10 (Milestone 3), M3's contract is a single function:

```go
func Simulate(paths []Path, numAnts int) ([]string, error)
```

Given the disjoint paths M2 found and the number of ants from the input file, M3 has to produce the exact turn-by-turn move lines that the program prints after the blank line — one string per turn, each turn listing every ant that moved that turn as `Lx-y` (`x` = ant number, `y` = room moved into), space-separated, only ants that actually moved.

The output has to respect the rules from PRD §6.2:

- an ant moves at most once per turn,
- the room an ant moves into must be empty at the end of that turn (start/end excepted),
- a tunnel is used at most once per turn,
- every ant ends up in the end room,
- the same input always produces the same output (determinism).

PRD Issue 3.1–3.3 breaks this into "distribute ants across paths," "simulate turns," and "format the moves." Issue 3.4 (print file + blank line + moves) is explicitly called out as overlapping with M4, but was wired into `main.go` as part of this milestone too (see §7).

## 2. What already existed before M3

- **M1 (`internal/parser`)** — `Parse(filePath) (*graph.Graph, error)`. Fully validated `*graph.Graph`: rooms, links, `NumAnts`, `Start`, `End`. M3 never touches raw input lines or validation; it trusts the `*graph.Graph` (indirectly, via M2's output).
- **M2 (`internal/graph`)** — `FindPaths(g) ([]Path, error)`. Returns the set of room-disjoint paths (as `[]Path`, where `Path = []string` room names) that minimizes turns for `g.NumAnts`, using a split-node max-flow model (`network.go`, `search.go`, `decompose.go`).

Critically, M2's `distribute.go` **already implemented the ant-distribution math** from PRD §7.6 — `tunnelCount`, `arrivalTurn`, and a greedy `antsPerPath` — because `FindPaths` needs to know, for each candidate flow value `k`, how many turns that many paths would take for `g.NumAnts` ants, in order to pick the best `k`. That existing code only returned *counts* per path, not *which ant numbers*, which is why M3 needed to extend it (see §4) rather than write the distribution logic from scratch.

So M3's job was narrower than a from-scratch simulation: turn already-computed paths and already-computed distribution math into concrete per-turn move strings.

## 3. M3 architecture

```
Parse           (M1, internal/parser)
  → *graph.Graph
FindPaths       (M2, internal/graph)
  → []graph.Path              (disjoint, shortest-first-augmented, best-k for NumAnts)
AssignAnts      (M2, internal/graph — extended for M3)
  → [][]int                   (which ant IDs ride which path, in queue order)
Simulate        (M3, internal/simulation)
  → []string                  (one line per turn, "Lx-y" moves)
Output          (main.go)
  → raw file + blank line + turn lines, to stdout
```

Responsibilities:

- **Parse** turns bytes into a validated graph. Nothing simulation-related.
- **FindPaths** turns the graph into the *set* of paths to use — already optimal for the ant count, already guaranteed disjoint.
- **AssignAnts** turns that path set into a concrete assignment: for each path, the ordered list of ant numbers that will travel it.
- **Simulate** turns that assignment into the literal turn-by-turn move strings.
- **main.go** wires the four stages together and produces the final stdout in the required format.

## 4. AssignAnts

### Why it exists

`Simulate`'s contract is `Simulate(paths []Path, numAnts int)` — it does not receive a pre-computed distribution. To emit `Lx-y` lines it needs to know, concretely, which ant number is at which position on which path. The graph package's existing `antsPerPath` only returned *how many* ants per path (`[]int`), which is enough to compute a turn count but not enough to label individual moves. `AssignAnts` is the same greedy algorithm, extended to record identity instead of just a count.

### How the greedy assignment works

Ants are hidden out one at a time, in order `1..numAnts`. For each ant, every path is asked "if you got this ant, added to whoever is already queued on you, when would it arrive?" — that's `arrivalTurn(path, alreadyQueued) = tunnelCount(path) + alreadyQueued`. The ant is handed to whichever path answers soonest (ties go to the earlier path index, since the comparison is strict `<`). This is exactly PRD §7.6's rule: *"assign each ant to the path that currently minimizes path_length + ants_already_assigned_to_it."*

### What the queue represents

`AssignAnts` returns `[][]int` — one `[]int` per path (same order/index as the input `paths` slice), holding the ant numbers assigned to that path **in the order they queue on it**. Because ants are processed `1..numAnts` in order and each is only ever appended to its chosen path's slice, each path's queue comes out already sorted ascending by ant number. Position `i` in that slice (0-indexed) is the ant's queue position — how many ants are ahead of it on that specific path.

### Why ant IDs are stored, not just counts

Labeling a move requires the real ant number (`Lx-y`), not a count. Storing the ID also captures, for free, the queue position (`i`, the slice index) that `Simulate`'s closed-form calculation needs — see §5.

### Why this avoids duplicating the existing distribution algorithm

`antsPerPath` (used internally by `FindPaths`/`turnsNeeded` to score candidate path sets) is now defined *in terms of* `AssignAnts`:

```go
func antsPerPath(paths []Path, ants int) []int {
	queues := AssignAnts(paths, ants)
	counts := make([]int, len(queues))
	for p, q := range queues {
		counts[p] = len(q)
	}
	return counts
}
```

There is exactly one implementation of the greedy rule. If `Simulate` re-implemented its own distribution loop instead of calling `graph.AssignAnts`, there would be two copies of the same algorithm that could silently drift apart — e.g. a future tweak to the tie-breaking rule in one copy but not the other would make `FindPaths`' chosen "best" path set inconsistent with what `Simulate` actually schedules, potentially producing a turn count that doesn't match what `FindPaths` promised.

### A small concrete example

Two paths, a 3-tunnel one and a 5-tunnel one, 6 ants (this is the worked example in both `distribute_test.go` and `simulation_test.go`):

| ant | path 0 arrival if chosen | path 1 arrival if chosen | chosen | queue after |
|---|---|---|---|---|
| 1 | 3+0=3 | 5+0=5 | path 0 | path0=[1] |
| 2 | 3+1=4 | 5+0=5 | path 0 | path0=[1,2] |
| 3 | 3+2=5 | 5+0=5 | path 0 (tie → lower index) | path0=[1,2,3] |
| 4 | 3+3=6 | 5+0=5 | path 1 | path1=[4] |
| 5 | 3+3=6 | 5+1=6 | path 0 (tie → lower index) | path0=[1,2,3,5] |
| 6 | 3+4=7 | 5+1=6 | path 1 | path1=[4,6] |

Result: `AssignAnts` returns `[[1,2,3,5], [4,6]]`.

## 5. Closed-form simulation

`FindPaths` guarantees the returned paths share no intermediate room (only start/end may be shared). That single guarantee is what makes a closed-form calculation possible: each path behaves as its own private single-lane corridor, and ants on different paths can never interact.

### What queue position `i` means

`i` is the 0-indexed slot of an ant within its path's queue from `AssignAnts` — `i=0` is the first ant sent down that path, `i=1` the second, and so on. It is exactly the "ants already queued ahead of it" value from `arrivalTurn`.

### What `turn` means

`turn` is a 1-indexed global simulation step, the same "turn" that becomes one line of output. Turn 1 is the first step in which any ant can move.

### Why `path[turn-i]` gives the ant's room

Think of a path as a shift register. The first ant on the path (`i=0`) enters the first room (`path[1]`) on turn 1, the second room (`path[2]`) on turn 2, and so on — on turn `t` it is at `path[t]`. The second ant (`i=1`) starts one turn later, so on turn `t` it is exactly where the first ant was on turn `t-1`, i.e. at `path[t-1]`. Generalizing, ant `i` is at `path[t-i]` on turn `t`. `path[0]` is the start room and is never a destination (the walk begins at index 1); `path[len(path)-1]` is the end room.

### Why an ant starts one turn after the ant before it

A room (other than start/end) can hold only one ant. If ant `i-1` enters `path[1]` on turn `1+(i-1)`, that room is occupied until ant `i-1` moves on to `path[2]` the next turn, at which point it is empty again — precisely in time for ant `i` to enter it. Starting any sooner would violate the one-ant-per-room rule; starting any later would waste a turn unnecessarily (PRD §7.6 calls the resulting schedule "provably optimal for a fixed set of paths"). One-turn spacing is therefore both required and sufficient.

### Why we don't need a mutable room-occupancy map

The formula `path[turn-i]` already encodes the exact room every ant occupies on every turn, for the entire run, without needing to simulate step-by-step state. There is nothing to "check" at runtime because the spacing (one turn per queue position) is fixed by construction — occupancy is a consequence of the formula, not a constraint the code has to enforce separately.

### Why the one-ant-per-room and one-tunnel-per-turn constraints still hold

- **One ant per room:** within a path, `path[turn-i]` gives every ant a distinct room on a given turn (different `i` → different `turn-i` for the same `turn`), by the argument above. Across paths, rooms cannot collide because M2 guarantees the paths share no intermediate room — the only rooms that could coincide across paths are `Start`/`End`, both explicitly exempt from the one-ant-per-room rule.
- **One tunnel per turn:** the tunnel between `path[p]` and `path[p+1]` on a given path is only ever crossed by the ant currently at position `p` moving to `p+1`, and at most one ant occupies position `p` on that path in a given turn (again by the one-turn-spacing argument) — so each tunnel is used by at most one ant per turn. Different paths never share a tunnel by construction (disjoint intermediate rooms implies disjoint tunnels between them).

### Worked example: a 3-tunnel path, 2 ants (`i=0`, `i=1`)

Path: `S, a, b, E` (`tunnelCount = 3`).

| turn | ant 1 (i=0) at path[turn-0] | ant 2 (i=1) at path[turn-1] | line |
|---|---|---|---|
| 1 | `path[1]=a` | — (not started, `turn-i=0` is out of range) | `L1-a` |
| 2 | `path[2]=b` | `path[1]=a` | `L1-b L2-a` |
| 3 | `path[3]=E` | `path[2]=b` | `L1-E L2-b` |
| 4 | — (`turn-i=4`, out of range `1..3`) | `path[3]=E` | `L2-E` |

This matches `TestSimulateOneShortPathCarriesAllAnts` in `simulation_test.go` (with a third ant added there for a fuller check), and the same mechanics — extended to two paths — are checked exactly in `TestSimulateMatchesTheBriefsWorkedExample` and `TestSimulateSplitsAntsAcrossTwoUnequalPaths`.

## 6. Output generation

### How moves are collected per turn

`Simulate` allocates `turnMoves := make([][]move, totalTurns)` (`totalTurns` from `lastArrival`, see below), then for every path and every ant in that path's queue, computes the ant's active turn range (`i+1` to `i+tunnels`) and appends a `move{ant, room}` to `turnMoves[turn-1]` for each turn in that range. Moves from every path land in the same per-turn buckets — nothing keeps a given turn's bucket organized by path.

`totalTurns` itself comes from `lastArrival`: the maximum, over all non-empty path queues, of `tunnels + (queueLength-1)` — i.e. the arrival turn of the *last* ant on each path, which is exactly `arrivalTurn(path, len(queue)-1)`. This is the same value `graph.turnsNeeded` computes internally when `FindPaths` scores candidate path sets, just re-derived here from the concrete `AssignAnts` queues.

### Why moves are sorted by ant number

Within one turn, moves can arrive from several paths in path order, not ant order — path 0's ants for that turn are appended before path 1's, even if path 1 has a lower-numbered ant active that turn. `formatTurns` sorts each turn's `[]move` by ant number before formatting, so the output is deterministic and reads in a natural, ascending order. (No example in the PRD shows a multi-path turn line, so this is a design choice, not a spec requirement — but it is the only requirement-compatible choice that's also fully deterministic regardless of path indexing.)

### How `Lx-room` strings are produced

`formatTurns` runs `fmt.Sprintf("L%d-%s", m.ant, m.room)` for each sorted move, then `strings.Join(parts, " ")` to build one line per turn.

### How multiple paths are combined into one turn

Because every path independently contributes zero or more moves to each `turnMoves[turn-1]` bucket, "combining" is just: collect from all paths into the same bucket, then sort and format. There is no cross-path coordination needed beyond that, since paths cannot collide (§5).

## 7. main.go integration

```
os.Args[1]
  → os.ReadFile(filePath)      → raw bytes, kept for verbatim printing
  → parser.Parse(filePath)     → *graph.Graph (re-reads the file itself)
  → graph.FindPaths(g)         → []graph.Path
  → simulation.Simulate(paths, g.NumAnts) → []string (turn lines)
  → stdout: raw file (trailing newline normalized to one) + blank line + turn lines
```

Every stage's error is handled identically: print `ERROR: invalid data format, <reason>` to stderr and `os.Exit(1)`. No stage panics; every failure path returns a Go `error` that `main` checks explicitly.

### Why the input file is read twice

`os.ReadFile(filePath)` is called once directly in `main` (to get the raw bytes for verbatim printing — PRD §6 requires printing "the original input file, unchanged"), and a second time inside `parser.Parse(filePath)` (which does its own `os.ReadFile` as part of M1's implementation). This was a deliberate choice, not an oversight: the alternative would be changing `Parse`'s signature/return value to also hand back the raw bytes or raw lines, which would modify the M1 contract (`func Parse(filePath string) (*graph.Graph, error)`) that M1's tests and M2/M3's understanding of the pipeline are built around. Re-reading a small text file a second time is negligible cost compared to the pathfinding and simulation work that follows, so the simpler, contract-preserving option was chosen over a cross-milestone signature change.

## 8. Tests

### Normal behavior

`TestSimulateMatchesTheBriefsWorkedExample` and `TestSimulateSplitsAntsAcrossTwoUnequalPaths` assert **exact** output strings against hand-computed expectations (the first against the PRD's own worked example, byte for byte; the second against the same 3-tunnel/5-tunnel/6-ant scenario worked through by hand in §4/§5 of this doc). These prove the formula produces the *literal* expected text, not just "a plausible-looking" schedule.

### Edge cases

- `TestSimulateOneShortPathCarriesAllAnts` — a single path carrying every ant (no path splitting at all), confirming the single-corridor queueing behavior still works when there's nothing to distribute.
- `TestSimulateRejectsNoPaths` / `TestSimulateRejectsNoAnts` — confirm `Simulate` returns an `error` (not a panic, not a zero-length silent success) for the two obviously-invalid inputs it defensively guards against.
- On the `graph` package side, `TestAssignAntsLeavesASlowPathEmpty` and `TestAssignAntsOnNoPaths` confirm `AssignAnts` behaves on empty queues/empty path sets without indexing out of range.

### Invariants

`checkInvariants` (used by `TestSimulateOnExampleFixtures`) doesn't compare against a fixed expected string — it re-parses every generated `Lx-y` token and checks the *properties* the audit cares about, generically, for any input: no ant number appears twice within one turn's line, no non-terminal room name appears twice within one turn's line (i.e., no room collision), and every ant's last recorded move lands it in a room that is some path's end room. This is what actually proves "ants alone in each room" and "each tunnel used at most once per turn" hold for real parsed input, rather than just trusting the closed-form derivation in the abstract.

### Deterministic output

`TestSimulateIsDeterministic` runs `Simulate` twenty times on the same input and asserts every run produces an identical `[]string`. This is structurally guaranteed (no map iteration, no randomness anywhere in `Simulate`/`AssignAnts`/`formatTurns` — only slices and a numeric sort), but the test exists to catch a regression if that ever stops being true, matching the same determinism-testing pattern already used in `graph`'s `TestFindPathsIsDeterministic`.

### Example/detour verification

`TestSimulateOnExampleFixtures` runs the **real pipeline** — `parser.Parse` → `graph.FindPaths` → `simulation.Simulate` — against the actual files `examples/example00.txt` and `examples/detour.txt`, asserting the turn count doesn't exceed the PRD's stated limit (6, for both) and that `checkInvariants` holds. This is the closest thing M3's test suite has to an integration test, and it's what the manual `go run . examples/...` checks (§7 of the implementation report) also confirmed by eye.

## 9. Important invariants and assumptions

**Guarantees `Simulate` relies on from M2 (`FindPaths`):**
- The paths returned share no intermediate room (only `Start`/`End` may repeat across paths). This is the single load-bearing guarantee the whole closed-form approach depends on.
- Each `Path` is a valid, contiguous walk from `Start` to `End` along real links.
- The path set is already the one that minimizes turns for the given `NumAnts` (i.e., `Simulate` does not need to reconsider *which* paths to use — that decision is final by the time `Simulate` runs).

**Logic implemented by M3 (not inherited):**
- Turning a path set + ant count into a concrete ant→path→queue-position assignment (`AssignAnts`).
- Turning that assignment into per-turn room positions via the closed-form formula (`Simulate`).
- Formatting and ordering the output lines (`formatTurns`).

**What would need to change if the disjointness guarantee changed:** if `FindPaths` ever returned paths that could share an intermediate room (e.g. a bug, or a deliberate future relaxation of the model), the closed-form approach in §5 would silently produce incorrect output — two ants from different paths could be placed in the same room on the same turn without any check catching it, because the formula assumes that can't happen rather than verifying it at runtime. In that scenario, M3 would need to switch to an explicit occupancy-tracking simulation loop (the approach PRD Issue 3.2 originally describes) that checks room emptiness before each move, at the cost of more code and mutable state. This is a real assumption, not an explicit written requirement — it is what the "Closed-form arithmetic (Recommended)" decision from the M3 planning phase deliberately traded off in exchange for simplicity, on the basis that M2's disjointness guarantee is itself a hard requirement of the flow model (§7.3 of the PRD), not an incidental property that might change casually.

## 10. Audit Questions

**Why did you create `AssignAnts`?**
Because `Simulate`'s contract only receives `paths` and `numAnts`, not a precomputed distribution, but it needs to know exactly which ant number is at which position on which path to label `Lx-y` moves. The existing `antsPerPath` only returned counts, which is enough to compute a turn count but not enough to generate labeled moves.

**Why is `AssignAnts` in the `graph` package, not `simulation`?**
Because the exact same greedy algorithm was already there (as `antsPerPath`, used internally by `FindPaths`/`turnsNeeded` to score candidate path sets). Keeping the algorithm in one place and exporting the richer version means `FindPaths`'s scoring and `Simulate`'s actual scheduling can never disagree about how ants are distributed — they call through to literally the same function.

**Why not duplicate the distribution algorithm in `simulation` instead?**
Duplication would mean two independent implementations of the same greedy rule that would have to be kept in sync by hand. If they ever diverged (different tie-breaking, an off-by-one in one but not the other), `FindPaths` could pick a path set on the assumption of one turn count, while `Simulate` produces a different actual schedule — a subtle, hard-to-notice correctness bug. Reuse eliminates that entire class of bug by construction.

**Why use closed-form simulation instead of a turn-by-turn occupancy loop?**
Because M2's `FindPaths` already guarantees the paths are room-disjoint, each path is provably a private single-lane corridor where ant `i` is at `path[turn-i]` on turn `turn` — a direct algebraic consequence of the one-turn-spacing argument in §5. Computing that directly is simpler and needs no mutable simulation state, while still satisfying every rule in PRD §6.2. (See §9 for the assumption this trades on.)

**Why no occupancy map?**
Because the occupancy is already implied by the formula — `path[turn-i]` for distinct `i` gives distinct rooms for a fixed `turn`, and distinct paths can't collide because they're disjoint. Tracking occupancy explicitly would be redundant bookkeeping for information the closed form already encodes.

**How do you prevent two ants from entering the same room in the same turn?**
Within a path: different queue positions `i` map to different rooms `path[turn-i]` for the same `turn`, since `turn-i` differs whenever `i` does. Across paths: M2 guarantees no two paths share an intermediate room, and `Start`/`End` (the only rooms that can repeat across paths) are explicitly exempt from the one-ant-per-room rule.

**How do you prevent two ants from using the same tunnel in the same turn?**
A given tunnel belongs to exactly one path (paths don't share intermediate rooms, so they don't share the tunnels between those rooms either) and is only crossed by whichever ant currently occupies the room before it — and only one ant occupies any given room-position on a path in a given turn, by the same one-turn-spacing argument.

**Why are moves ordered by ant number?**
Multiple paths independently contribute moves to the same turn, in path order, not ant order — without an explicit sort, ant 4 from path 1 might print before ant 1 from path 0. Sorting by ant number gives one deterministic, natural-reading order regardless of path indexing. (This is a design choice for a case the PRD's own examples don't cover — see §6.)

**Why does `main.go` read the file twice?**
Once directly, to keep the raw bytes for verbatim printing (PRD §6 requires printing the input unchanged); once inside `parser.Parse`, which does its own read as part of the M1 contract. Changing `Parse` to also return raw bytes would mean modifying the M1 function signature that M1's own tests and the rest of the pipeline are built around, for a cost (one extra small file read) that's negligible next to path-finding and simulation.

**What happens with invalid input?**
Each stage (`os.ReadFile`, `parser.Parse`, `graph.FindPaths`, `simulation.Simulate`) returns a Go `error` on failure. `main` checks every one explicitly and, on any failure, prints `ERROR: invalid data format, <reason>` to stderr and exits with status 1. Nothing panics.

**What happens with zero ants or empty paths?**
`Simulate` explicitly guards both: `len(paths) == 0` and `numAnts < 1` each return a distinct `error` before any computation happens. In practice `numAnts < 1` should already be rejected by `parser.Parse` (ant count must be a positive integer) and `len(paths) == 0` by `graph.FindPaths` (a disconnected start/end returns an error before `Simulate` is ever called) — the guards in `Simulate` are defensive, consistent with the rest of the codebase's style of never trusting an invariant it can cheaply check itself, and with the PRD's blanket requirement to never panic or hang on any input.

**How is deterministic output guaranteed?**
`AssignAnts` processes ants in a fixed numeric order (`1..numAnts`) against a fixed input `paths` slice, with strict (not `<=`) comparisons so ties always resolve to the lower path index. `Simulate`'s per-turn move collection and `formatTurns`'s sort are both driven by that same fixed structure — no map iteration or other non-deterministic ordering is used anywhere in the M3 code path. `TestSimulateIsDeterministic` and `TestFindPathsIsDeterministic` (M2) both check this empirically.

## 11. Code walkthrough

**`internal/graph/distribute.go`**
- `tunnelCount(p Path) int` — `len(p) - 1`; how many moves it takes to walk a path.
- `arrivalTurn(p Path, queuedAhead int) int` — `tunnelCount(p) + queuedAhead`; the turn at which an ant queued behind `queuedAhead` others on this path would arrive.
- `AssignAnts(paths []Path, numAnts int) [][]int` — the greedy assignment loop (§4). Calls `arrivalTurn` for every path on every ant to pick the soonest-arriving path.
- `antsPerPath(paths []Path, ants int) []int` — now a thin wrapper: `len()` of each `AssignAnts` queue.
- `turnsNeeded(paths []Path, ants int) int` — used by `FindPaths` to score candidate path sets; takes the max `arrivalTurn` over all non-empty paths, using `antsPerPath`'s counts.

**`internal/simulation/simulation.go`**
- `move` — a tiny `{ant int; room string}` struct, the unit `Simulate` collects per turn.
- `Simulate(paths []graph.Path, numAnts int) ([]string, error)` — validates inputs, calls `graph.AssignAnts`, computes `totalTurns` via `lastArrival`, fills `turnMoves` using the closed-form `path[turn-i]` calculation (§5), then calls `formatTurns`.
- `lastArrival(paths []graph.Path, queues [][]int) int` — the M3-side re-derivation of `arrivalTurn(path, len(queue)-1)`'s maximum, computed directly from the concrete `AssignAnts` queues rather than by calling back into `graph`'s unexported `turnsNeeded`.
- `formatTurns(turnMoves [][]move) []string` — sorts each turn's moves by ant number and renders them as `Lx-y` strings (§6).

**`main.go`**
- Reads `os.Args[1]`, reads the raw file bytes, calls `parser.Parse`, `graph.FindPaths`, `simulation.Simulate` in sequence, checking each `error` the same way.
- Prints the raw file content (newline-normalized), a blank line, then the joined turn lines — see §7.
